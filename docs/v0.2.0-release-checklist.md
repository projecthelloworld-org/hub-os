Status: implementation in progress. The published v0.1.0 installer remains the stable release until every gate below is verified.

## Foundation checkpoint — 2026-10-13

Implemented on `codex/community-monitoring-v02`: source-driven collection targets, discovery of built-in and explicitly enabled trusted local plugins, protocol checks and a synthetic starter package, mixed community-site demo with unchanged canonical IDs, additive mapping/classification migration, sanitized numeric evidence, bounded upstream request helper, credential references, stale-job reclaim with lease fencing and deadline cancellation.

Verified locally: Bun tests (including fixture failure/privacy tests), isolated PostgreSQL integration tests (fresh migrations, many-identifiers mapping, lease recovery, generic added-plugin telemetry and a v0.1 schema upgrade), JavaScript checks, Compose validation and existing Bash syntax checks. The suite also runs in the exact Bun 1.3.14 container used by the product. Dependency auditing reported no advisories for the current eight locked packages. This checkpoint does **not** establish dashboards, live adapters, alert routing, full installation, backups or release readiness.

Reproduce the isolated database checks from the repository root:

```bash
docker compose -p hubos-v02-foundation-test -f compose/test.compose.yaml up -d --wait db
docker compose -p hubos-v02-foundation-test -f compose/test.compose.yaml run --rm migrate
cd services/hubos
HUBOS_TEST_DATABASE_URL=postgresql://hubos_test:fixture-only-not-for-deployment@127.0.0.1:15432/hubos_test bun test
```

The fixture database name and local host are checked before tests can truncate it. The fixture password is deliberately public and must never be used for a deployment. To clean up only these disposable fixtures, run `docker compose -p hubos-v02-foundation-test -f compose/test.compose.yaml down --volumes` from the repository root.

Foundation CI passed for commit `458f6a5`: [CI run](https://github.com/projecthelloworld-org/hub-os/actions/runs/38400741451). Subsequent changes still require their own CI verification before release. No v0.2.0 tag or release has been created.

## Kuma and incident checkpoint — 2026-10-13

Added the digest-pinned Kuma 2.5.6 service and isolated Socket.IO adapter, private generated metrics key, supported metrics collection with latest-heartbeat freshness checks, source-scoped generic webhooks/provisioning, vendor-neutral monitors and coverage-aware SQL views. Infrastructure monitors have no fictional site. Incident transitions are transactionally deduplicated and ordered; notification delivery has PostgreSQL leases/retries and local Mailpit delivery.

Verified 61 local tests, including actual fresh/repeat Kuma provisioning, unchanged custom monitor edits and account, real authenticated native outage/recovery webhooks, pause-as-unknown, concurrency, weighted observation coverage and email delivery. A fresh full Compose test on separate loopback ports completed both provisioners with exit code 0, created two infrastructure plus ten synthetic monitors, and delivered its demo fault notification. Repeat Kuma Compose provisioning kept twelve monitors and one opening notification. Bun 1.3.14 compatibility, Compose validation and dependency auditing also passed; HubOS now pins Nodemailer 10.1.0 because the older client failed security auditing.

The running disposable full-stack project is `hubos-v02-monitoring-compose-test` (HubOS 10880, Metabase 13001, Kuma 13012, Mailpit 18035); these are fixture services, not a deployed production release. Existing non-test deployments were not reset. CI now runs the isolated Kuma integration suite, but each new implementation commit still requires a verified CI result.

Still pending: Metabase dashboards/data-alert definitions and read-only account, initial live adapters, protected administration/operator authentication, full demo/live installer wiring, backup/restore and release/public installer gates. The current `install.sh` still serves the unchanged v0.1.0 release and has not been relabelled v0.2.0.

## Metabase implementation checkpoint — 2026-10-13

Implemented reporting views, a view-only analytics login, four native dashboard templates with 15 questions, site/country/UTC-date filter mappings, generic telemetry, and eight native active/recovery alert questions. Added the source-scoped Metabase webhook plugin, private header authentication, explicit canonical-site mapping policy and interrupted-setup resource tracking. Dashboard/question edits are preserved by tracking resource IDs rather than replacing resources on restart.

The isolated live Metabase run created the reporting connection, two collections and 15 questions, then exposed a compatibility issue with Metabase's normalized query representation while laying out the first dashboard. That issue was corrected in the source. The next run became uninspectable when the local Docker engine and Metabase HTTP endpoint stopped responding; OrbStack's configuration diagnostics report running/configured, but direct engine and HTTP health requests time out. No full dashboard, alert-delivery, or visual acceptance is claimed yet. Remaining runtime verification must resume against the current containers/volumes after responsiveness returns, not reset existing user deployments.

At this checkpoint, 55 unit/fixture tests, JavaScript checks, Compose validation and dependency auditing pass. New isolated PostgreSQL read-only/aggregate-signal tests are implemented but not yet run locally after the engine stalled; repository CI is the next independent verification path. Fresh/repeat Metabase setup, actual filter queries, native alert/recovery delivery, and desktop/narrow visual inspection remain release gates. Metabase v0.60.7 is the currently exercised upstream baseline; its support/security status must be reviewed before release.

## Scope

Vanilla JavaScript on Bun, PostgreSQL and Dbmate. Community sites are the primary concept; the synthetic demonstration contains five Ugandan and five Angolan sites, including schools, community centres and libraries. Local fixtures and local Headwind/ODK instances establish tested compatibility, not certification against every real deployment.
